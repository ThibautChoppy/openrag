01 Budget VRAM & RAM

Ce qui tient seul, ce qui ne tient pas ensemble

openrag met trois modèles en concurrence sur le même serveur JIT (LM Studio) — LLM, embedder, VLM — et consomment de la VRAM. Reranker, Whisper et Marker vivent tous les trois sur CPU — ils consomment de la RAM, jamais de VRAM. Coche ce qui tourne à l'instant T pour voir les deux jauges bouger.

VRAM mesurée à chaque fois, pas estimée à partir de la taille du fichier GGUF : LLM 9,8 Go, Embedder 7,5 Go, VLM 5,8 Go (Q4_K_M — Q5_K_M n'existait pas pour ce modèle).

✓

Le calcul se vérifie : seuls 3 rôles sur 6 touchent la GPU. Le pic VRAM reste celui du plus gros modèle JIT chargé seul — 9,8 Go mesurés — quel que soit l'usage du reranker, de Whisper ou de Marker en parallèle, puisque les trois tournent à 0 Go de VRAM. Marge confortable de 6,2 Go sur les 16 Go, en toutes circonstances.

⚠

Le vrai piège n'est pas la taille des modèles, c'est le nombre de rôles GPU par requête. Une requête de chat avec RAG + images a potentiellement besoin de l'embedder, du VLM et du LLM dans le même échange. Si les trois vivent sur le même serveur JIT, chaque tour paie un aller-retour décharge/recharge. C'est un compromis à accepter, pas un bug à corriger — et le CPU pour les trois autres rôles en est un autre, assumé pour la même raison : vitesse d'indexation contre marge VRAM.

Ⓘ

La RAM n'est, elle, jamais le facteur limitant. Même en cochant tout ci-dessus (les 3 rôles GPU + les 3 rôles CPU + Milvus), le total plafonne autour de 21,6 Go sur 32 Go — 10 Go de marge dans le pire cas réaliste. Contrairement à la VRAM, la RAM n'impose pas de discipline JIT ici.

Ⓘ

Disque ≠ VRAM. L'image Infinity ROCm qu'on a supprimée pesait 104 Go sur disque (des installations PyTorch dupliquées dans l'image) — le modèle lui-même n'a jamais eu besoin que d'environ 0,8 Go de VRAM, et n'en a plus besoin du tout maintenant qu'il est hébergé sur CPU. Trois ressources différentes (disque, VRAM, RAM), trois problèmes différents, résolus séparément.

04 Vérifications de code & d'image

Ray, Milvus, Infinity : l'adhérence réelle, pas supposée

Trois affirmations à vérifier avant de replanifier — code lu, pas deviné.

Partiellement vrai

Ray va au-delà de Marker/OCR

@ray.remote dans indexer_actor.py, marker_workers.py, docling_workers.py, whisper_workers.py, task_state.py — toute la chaîne d'indexation, pas que l'OCR.

Mais : aucun ray. dans le chemin chat/recherche. Le coût réel n'existe que pendant l'indexation active.

Meilleur que prévu

Milvus est déjà abstrait — et le switch a un vrai intérêt

core/vector_stores/vector_store.py définit une ABC VectorStore générique. MilvusVectorStore en est la seule implémentation ; écrire ChromaVectorStore est un travail scopé.

Mais pas pour la vitesse : à ton échelle (corpus personnel, largement sous le million de vecteurs), Milvus et ChromaDB délivrent un rappel quasi-exact — la différence de latence est inaudible. Le vrai gain est l'empreinte RAM : 8 Go recommandés pour Milvus+etcd+MinIO contre ≈0,8 Go pour ChromaDB en mono-process. Vigilance : pas d'équivalent natif au hybride dense+BM25 de Milvus dans ChromaDB, à réimplémenter côté client.

Résolu et testé

Reranker : deux impasses avant la bonne solution

1. L'image infinity:latest-rocm (104 Go) embarquait plusieurs installations PyTorch dupliquées, pas construite via CI/CD à cause de sa taille (issue publique #94 du dépôt) — défaut connu de cette image précise.

2. Plan de repli llama.cpp + GGUF communautaire (gpustack/gte-multilingual-reranker-base-GGUF) : échec au chargement, unknown model architecture: 'new' — cette conversion vient du fork patché de gpustack (llama-box), pas de llama.cpp vanilla.

Solution retenue et testée : michaelf34/infinity:latest-cpu (déjà présent dans extern/reranker/infinity.yaml), charge le modèle HF directement. Requête /rerank réelle envoyée — classement correct (0,95 sur le bon document). ≈1 Go de RAM, 0 Go de VRAM.

06 Piste d'allègement

Ce que je changerais, dans l'ordre

Garder tel quel

  • Marker CPU-only — le précédent qui a guidé tout le reste : « ça marche, juste plus lent » s'applique aussi bien au reranker et à Whisper.
  • Ray — coût réel seulement à l'indexation, pas au chat.
  • ChromaDB bundled côté Open WebUI — inutile d'y toucher, c'est déjà léger.
  • Reranker sur michaelf34/infinity:latest-cpu — testé, ne pas retenter llama.cpp pour ce modèle précis (architecture GGUF incompatible).

Fait et testé en conditions réelles

  • LLM, Embedder, VLM : téléchargés, chargés dans LM Studio, interrogés individuellement (chat, embedding, description d'image) — VRAM mesurée, pas estimée : 9,8 / 7,5 / 5,8 Go.
  • Reranker : requête /rerank réelle envoyée à Infinity CPU, classement correct confirmé.
  • LM Studio reconfiguré en 0.0.0.0 (était repassé en 127.0.0.1 après un relancement GUI — invisible depuis un conteneur Docker sinon) ; vérifié joignable depuis un conteneur via host.docker.internal.

À instruire avant de coder

  • ChromaDB côté openrag : écrire ChromaVectorStore pour récupérer ≈7,2 Go de RAM (Milvus → Chroma), puis décider du hybride dense+BM25.
  • Open WebUI : vision supportée au chat, pas câblée dans le pipeline Knowledge par défaut (OCR, pas légendage) — voir le graphe Open WebUI.
  • Whisper et Marker : chiffres RAM encore des estimations documentées, pas mesurées comme les 3 modèles GPU et le reranker — à valider sur un vrai document/fichier audio.
